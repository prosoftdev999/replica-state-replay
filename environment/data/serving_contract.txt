Inference replay notes

The files in this directory are surviving records from the serving path involved in the monitoring gap. Fields ending in `_us` are microseconds. Assignment windows use half-open intervals: a record is valid at its start and no longer valid at its end. A journal row remains in force until a later row for the same scope replaces it.

Feature schemas, model snapshots, normalizer revisions, deployment journals, post-processing journals, residual-corrector journals, and calibration journals are versioned service records rather than a single final configuration. Revisions recorded after an inference must not be applied retroactively. Clock beacons are paired coordinator/local observations captured during the incident; replica drift was not constant across the full interval.

Request rows reference feature packets by an epoch and packet slot. Packet slots are reused between epochs, so both fields belong to the packet identity.

The serving path carries a replica-local residual correction in addition to the archived model score. `residual_seeds.csv` records the residual state immediately before the first captured request on each replica. Every captured request advances that state, including requests outside the review set, so replay order matters. `residual_params.csv` is a legacy archive: the `format_rev` identifies a packing convention, and the physical x0..x2 positions do not carry stable semantic names across formats. The exact state transition used by each format revision must be recovered from the surviving known-good behavior; do not assume that a position has the same role merely because its numeric range looks familiar.

A second stateful correction is shared by calibration lanes rather than by serving replica. Each feature packet carries a `lane_key`; `lane_windows.csv` gives the time-qualified lane identity, and those key-to-lane assignments can change during the incident. `calibration_seeds.csv` records each lane state before the first captured request. Requests from all replicas advance lane state in coordinator-time order, so replaying replicas independently is not equivalent to replaying the serving path.

For a calibration revision, the lane state is added to the pre-policy score before probability and decision are produced. The next lane state is an affine combination of the previous lane state, the centered probability, and the standardized feature named by that revision's `basis_token`. `calibration_params.csv` stores those three coefficients in q0..q2, but their physical order is a legacy packing convention selected by `format_rev`; q positions do not have stable meaning across formats. The packing must be established from surviving known-good behavior rather than inferred from column position.

`replay_samples.csv` contains known-good outputs from unaffected requests handled by the same serving path. It is retained as operational evidence of the behavior that must be reconstructed for the review set. Parameter columns in the archived model, normalization, policy, residual, and calibration tables preserve service-era field names. A `format_rev` denotes the packing convention used by that archive record; different format revisions are not guaranteed to assign the same operational meaning to the same physical parameter position. Their meaning must be established from the surviving behavior rather than assumed from column names or position.

The serving workers also carried a short-lived queue-pressure offset reconstructed from dispatcher telemetry. Dispatcher timestamps use their own clock; `dispatcher_beacons.csv` contains paired coordinator/dispatcher readings from the incident. Each feature packet records the worker key that handled it, and `worker_windows.csv` gives the time-qualified mapping from that key to a pressure pool. Keys were reassigned during the window, so the current pool must be resolved at the request time.

`pressure_events.csv` records signed pressure pulses by pool. A pool begins at the state in `pressure_seeds.csv`. At each pressure event, use the pressure revision active at that event time from `pressure_journal.csv` and update the pool state as `state = decay * state + gain * pulse`, with `decay` and `gain` taken from `pressure_params.csv`. Requests do not advance this accumulator. The pool state current at an inference is added to the pre-policy score alongside the residual and calibration corrections. Dispatcher events and inference requests therefore have to be compared on coordinator time before replaying the final score.

Feature packet cache

The feature recorder did not emit complete vectors during this incident. Each row in `feature_packets.csv` is an innovation against the current state of a feature-cache bank. The row's `cache_key` is only a handle; `feature_cache_windows.csv` gives its time-qualified bank assignment, and those assignments changed while the capture was running. `feature_cache_seeds.csv` records the bank contents immediately before the first captured request.

Cache maintenance ran independently of inference. `feature_cache_events.csv` records additive maintenance changes to individual bank contents, and its timestamps are on the cache recorder's clock. `cache_beacons.csv` contains paired coordinator/cache readings from the incident. Cache maintenance and requests must therefore be placed on the same coordinator timeline before packet innovations are applied.

For an inference request, map p0..p3 through that request's schema revision to semantic feature tokens, add those innovations to the current bank vector, and use the resulting vector for inference. The bank is then replaced by that resulting vector. Cache maintenance events update the named semantic components but do not themselves create an inference request. Every captured request updates its bank, including requests outside the review set.
